# Русский LLM-роутер

Единый API, который выбирает языковую модель под задачу с учётом качества, стоимости, задержки и доступности провайдеров.

## Интерактивно оценить свой сценарий

**[▶ Открыть калькулятор нагрузки и бюджета](https://therxl.github.io/ru-llm-router/)**

Меняйте количество запросов, долю coding-задач, токены, тарифы моделей, число вызовов на запрос, пиковый множитель и задержку. Калькулятор пересчитает RPS, объём токенов, ожидаемую конкурентность, суточную/месячную стоимость и покажет, укладывается ли оценка в ваш бюджет. Работает в браузере, без API-ключей; введённые данные не отправляются.

> GitHub README не исполняет JavaScript, поэтому интерактивные поля не могут работать прямо внутри текста README. Калькулятор вынесен на GitHub Pages; исходник находится в [calculator/index.html](calculator/index.html).

## Быстрый ориентир для стартового сценария

При 1 000 запросов в сутки, 4 000 входных и 1 000 выходных токенов на запрос, одном вызове модели и условном тарифе $0,10 за 1 млн входных и $0,40 за 1 млн выходных токенов:

| Показатель | Оценка |
|---|---:|
| Средняя нагрузка | 0,0116 запроса/с |
| Входные токены в сутки | 4 млн |
| Выходные токены в сутки | 1 млн |
| Всего токенов в сутки | 5 млн |
| Условная стоимость в сутки | $0,80 |
| Условная стоимость за 30 дней | $24 |

Это иллюстрация, не прогноз и не актуальный прайс. Фактическая цена зависит от выбранных моделей, распределения задач, контекстного кэширования, повторов и действующих тарифов. Пиковую конкурентность следует считать по длительности запросов и проверять нагрузочным тестом.

## Как устроен поток запроса

1. Клиент отправляет запрос в единый API.
2. Роутер определяет класс задачи и ограничения: качество, бюджет, задержку, контекст.
3. Из каталога выбираются совместимые модели и применяется политика маршрутизации.
4. Адаптер вызывает провайдера; при временной ошибке возможен ограниченный fallback.
5. Клиент получает нормализованный ответ, система записывает метрики и расчётную стоимость.

## Цели проекта

- Один API вместо отдельных интеграций с каждым провайдером.
- Недорогие модели для простых задач и более сильные — для coding и сложного рассуждения.
- Прозрачные причины выбора модели, ограничения бюджета и наблюдаемость.
- Возможность менять модели и правила без изменения клиентского приложения.

## Статус и ближайшие шаги

Сейчас репозиторий содержит требования, первичные расчёты, архитектурное описание, roadmap и калькулятор. Следующий этап — минимальный API, каталог моделей, один адаптер провайдера, тесты маршрутизации и сбор реальных метрик. Это пока не готовый production-сервис.

## Принципы

1. Бенчмарки помогают отбирать кандидатов, но выбор проверяется на собственном наборе задач.
2. Маршрутизация учитывает качество, стоимость, задержку и доступность.
3. Повторы и fallback ограничиваются числом попыток и бюджетом.
4. Секреты и полный текст запросов не сохраняются в логах по умолчанию.
5. Экономия оценивается вместе с качеством ответа, а не только по цене токенов.
