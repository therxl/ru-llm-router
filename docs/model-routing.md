# Архитектура и маршрутизация моделей

## Цель

Роутер на Go предоставляет единый интерфейс к моделям и помогает выбрать подключение под задачу. Это **инструмент пользователя**, а не закрытый шлюз, который диктует допустимые модели или централизует их оплату.

Пользователь может подключить внешние API, локальный inference server или собственный endpoint. Он сам оплачивает услуги внешних провайдеров и несёт расходы на свою локальную инфраструктуру. Роутер не хостит локальные модели и не берёт на себя стоимость их вычислений.

## Компоненты

1. **Go API** — единый формат запроса/ответа, валидация и request ID.
2. **Connection registry** — пользовательские подключения: endpoint, модель, тип API, возможности и необязательные тарифы.
3. **Task/profile hints** — задача может быть явно задана клиентом; классификация — опциональная помощь, а не обязательный барьер.
4. **Routing policy** — пользовательские предпочтения по модели, цене, качеству, задержке и доступности.
5. **Adapters** — перевод общего интерфейса в API подключённой модели.
6. **Optional telemetry** — latency, usage, ошибки и оценка стоимости, если провайдер предоставляет данные.

## Принципы выбора

1. Принять запрос через единый API.
2. Учитывать выбранную пользователем модель, профиль задачи и его предпочтения.
3. Не исключать подключение только потому, что его нет в рекомендуемом каталоге; проверять только техническую совместимость и явно заданные пользователем ограничения.
4. Если пользователь разрешил автоматический выбор, ранжировать доступные подключения по выбранным критериям.
5. Выполнить запрос через адаптер и нормализовать ответ.
6. Повторять запрос или переключаться на другой endpoint только в соответствии с настройками пользователя и безопасными ограничениями повторов.
7. Возвращать диагностические сведения о маршруте, не раскрывая секреты.

## Режимы маршрутизации

- **Explicit** — пользователь задаёт конкретное подключение/модель.
- **Task profile** — пользователь выбирает профиль, например coding или general, а роутер предлагает подходящий endpoint.
- **Preference-based** — автоматический выбор с приоритетом цены, latency или заданного качества.
- **Fallback (опционально)** — переключение на резервное подключение, только если пользователь его разрешил.

Не следует вводить скрытые ограничения, обязательную эскалацию или обязательный централизованный биллинг. Поведение должно быть объяснимым и настраиваемым.

## Локальные модели

Локальная модель — это пользовательское подключение к запущенному пользователем runtime/API (например, совместимому с OpenAI API). Роутер хранит конфигурацию подключения, но не скачивает веса, не запускает inference автоматически и не оплачивает вычисления. В документации стоит явно указать, что локальный endpoint должен быть доступен процессу роутера, а безопасность и доступ к нему контролирует пользователь.

## Каталог и бенчмарки

Встроенные примеры моделей и бенчмарки — рекомендации, а не белый список. Пользователь должен иметь возможность добавить произвольный совместимый endpoint. Сравнивайте модели на собственных задачах; внешние бенчмарки не гарантируют качество на конкретном проекте.

## Минимальная конфигурация подключения

- имя подключения и provider/type;
- base URL и способ авторизации (секреты — только вне репозитория);
- model ID;
- поддерживаемые функции и лимиты контекста, если известны;
- необязательные цены/единицы тарификации и источник данных;
- необязательные метрики latency и результаты пользовательских тестов.

## Безопасность и надёжность

- Секреты хранить вне Git и не возвращать в диагностике.
- Не логировать содержимое запросов/ответов по умолчанию.
- Таймауты и повторы делать настраиваемыми.
- Не переключать на другой endpoint, если это противоречит выбору или ограничениям пользователя.
- Не считать локальный inference бесплатным: его расходы принадлежат владельцу инфраструктуры, даже если API не тарифицируется по токенам.

## Предлагаемый API

Для совместимости можно начать с `POST /v1/chat/completions` и общего формата сообщений. Дополнительные необязательные поля: `connection`, `task_profile`, `routing_mode`, `preferences`. Точный контракт следует зафиксировать тестами и не обещать полную совместимость с каким-либо API до прохождения этих тестов.
