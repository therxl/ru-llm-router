# Архитектура и маршрутизация моделей

## Компоненты

1. **API gateway** — аутентификация, квоты, нормализация запросов и ответов.
2. **Task classifier** — класс задачи: simple, coding, reasoning, long-context, extraction и т. п. Клиент может указать класс явно.
3. **Model registry** — модели, возможности, контекстные ограничения, тарифы, статус провайдера и результаты оценки.
4. **Policy engine** — отбор и ранжирование по качеству, стоимости, задержке и доступности.
5. **Provider adapters** — единый внутренний интерфейс к разным API.
6. **Fallback / escalation** — контролируемый переход на резервную или более сильную модель.
7. **Telemetry** — request ID, маршрут, токены, latency, ошибки и расчётная стоимость.

## Алгоритм выбора

1. Проверить API-ключ клиента, квоты и размер запроса.
2. Определить класс задачи и ограничения: бюджет, latency, контекст, tool calling и structured output.
3. Исключить несовместимые или недоступные модели.
4. Исключить модели, превышающие жёсткие бюджетные или контекстные лимиты.
5. Выбрать кандидата по профилю качества/цены/latency на основе версионированных оценок.
6. Выполнить запрос через адаптер, нормализовать ответ и записать метрики.
7. При временной ошибке сделать ограниченный retry или fallback.
8. При сигнале низкого качества разрешить эскалацию, если остаётся бюджет.

## Стартовые профили

| Класс | Начальная политика | Проверка качества |
|---|---|---|
| Классификация/извлечение | Самая дешёвая совместимая модель | Точность полей, schema validation |
| Общие вопросы | Экономичная модель, если проходит порог | Эталонный набор и человеческая оценка |
| Coding | Лучший результат на собственном coding-наборе в рамках бюджета | Unit tests, patch acceptance, code review |
| Сложное рассуждение | Более сильная модель в рамках бюджета | Рубрика решения и проверка корректности |
| Длинный контекст | Модель с подходящим контекстным окном | Retrieval/needle tests и точность |

Не зашивайте в код утверждения, что конкретная модель «лучшая». Храните результаты тестов, тарифы и возможности в каталоге с датами обновления.

## Внешние ориентиры для оценки

- SWE-bench Verified / SWE-bench Pro — задачи изменения реальных репозиториев; учитывайте различия наборов, загрязнение данных и методику запуска.
- LiveCodeBench — оценка программирования с временным контролем.
- HumanEval / MBPP — исторические ориентиры, недостаточные сами по себе для выбора coding-модели.
- Собственный русскоязычный набор — реальные типы задач проекта, тесты и понятная рубрика оценки.

Сравнивайте результаты с сопоставимыми версиями наборов, инструментами, лимитами, промптами и бюджетами. Храните версии тестов и избегайте персональных данных.

## Минимальная запись каталога

- provider, model_id, enabled;
- context_limit и поддерживаемые capabilities;
- цены входных/выходных токенов, валюта, дата обновления и источник;
- оценки latency с датой и методом измерения;
- результаты оценки по наборам и версиям;
- лимиты параллельности, rate limits и статус доступности.

## Надёжность и безопасность

- API-ключи хранить только в переменных окружения или менеджере секретов.
- По умолчанию не хранить полный текст запросов и ответов в логах.
- Ограничивать длину контекста, число повторов, конкурентность и стоимость.
- Использовать circuit breaker и таймауты на уровне провайдера.
- Не делать fallback, нарушающий privacy-, региональные или модельные ограничения клиента.
- Учитывать, что повторный вызов может тарифицироваться повторно.

## API-контракт первого среза

Можно начать с POST /v1/chat/completions с совместимым форматом сообщений и дополнительными необязательными полями task_profile, max_cost, latency_budget_ms и routing_mode. Возвращайте нормализованный ответ и request ID. Совместимость следует подтвердить тестами.
