# Пользовательские истории

Приоритеты: **P0** — необходимо для MVP; **P1** — важно после базового рабочего контура. Роутер предоставляет интерфейс и рекомендации; подключение моделей, выбор режима, ограничения и разрешение fallback остаются под контролем пользователя. Внешние API и локальные endpoints — пользовательские подключения; роутер не оплачивает их использование и не хостит локальные модели.

## US-01. Единый API
**Как** разработчик приложения, **я хочу** отправлять запросы через единый API, **чтобы** не зависеть от интерфейса конкретного LLM-провайдера.

Критерии приёмки: документированный endpoint и единый формат ответа; нормализованные ошибки; клиент указывает профиль задачи и ограничения без знания внутренних ID провайдеров. **P0**

## US-02. Автоматический выбор модели
**Как** клиент, **я хочу**, чтобы роутер выбирал подходящую модель автоматически, **чтобы** не поддерживать собственную таблицу соответствий.

Критерии: пользователь может явно выбрать подключение или включить автоматический выбор; учитываются задача и предпочтения; причина выбора объяснима; произвольные совместимые endpoints можно добавить вручную. **P0**

## US-03. Контроль стоимости
**Как** владелец продукта, **я хочу** оценивать стоимость запроса и ограничивать бюджет, **чтобы** контролировать расходы.

Критерии: если тарифы и usage доступны, показывается предварительная/фактическая оценка; цены можно задать вручную; ограничение бюджета или перенаправление — только если пользователь включил такую политику. Локальные расходы пользователь учитывает самостоятельно. **P0**

## US-04. Ограничение задержки
**Как** разработчик, **я хочу** задавать целевую задержку, **чтобы** роутер не выбирал заведомо медленный маршрут.

Критерии: лимит времени на запрос; измерение TTFT и полной latency, если доступны; документированный fallback. **P1**

## US-05. Сильный профиль для программирования
**Как** разработчик, **я хочу** направлять задачи по коду к моделям с подтверждёнными coding-возможностями, **чтобы** получать более надёжные изменения.

Критерии: отдельный класс coding; сравнение по релевантным бенчмаркам и собственному набору задач; сохранение версии модели и результатов оценки. **P0**

## US-06. Дешёвый маршрут для простых задач
**Как** владелец продукта, **я хочу** направлять простые вопросы к недорогим моделям, **чтобы** не переплачивать за избыточное качество.

Критерии: определены простые классы задач; дешёвый маршрут включается при приемлемом качестве на тестах; измеряется доля успешных дешёвых маршрутов. **P0**

## US-07. Эскалация при низкой уверенности
**Как** пользователь, **я хочу**, чтобы сложная задача могла перейти к более сильной модели, **чтобы** снизить риск некачественного ответа.

Критерии: эскалация отключена по умолчанию либо явно настраивается пользователем; заданы условия и максимум попыток; fallback не меняет выбранное подключение без разрешения пользователя. **P1**

## US-08. Политики маршрутизации
**Как** администратор, **я хочу** задавать правила по цене, качеству и latency, **чтобы** адаптировать систему под разные продукты.

Критерии: версия политики и проверка до публикации; безопасная конфигурация по умолчанию; возможность отката. **P0**

## US-09. Каталог моделей
**Как** оператор, **я хочу** видеть возможности и ограничения моделей, **чтобы** роутер не выбирал несовместимый endpoint.

Критерии: подключение хранит endpoint, модель, возможности и необязательные тарифы; каталог-пример не является белым списком; пользователь может добавлять собственные и локальные endpoints. **P0**

## US-10. Бенчмарки и собственная оценка
**Как** ML/QA-инженер, **я хочу** сравнивать кандидатов на одинаковом наборе задач, **чтобы** выбирать модель по измеряемому качеству.

Критерии: версия набора и параметры запуска; русскоязычный coding-набор; указание версий и ограничений внешних бенчмарков. **P1**

## US-11. Метрики и аудит
**Как** оператор, **я хочу** видеть стоимость, latency, ошибки и выбранные маршруты, **чтобы** находить регрессии и контролировать расходы.

Критерии: агрегация по классу задач, модели и провайдеру; секреты не попадают в логи; содержимое запросов не сохраняется по умолчанию; причина выбора доступна по request ID. **P0**

## US-12. Квоты и защита от злоупотреблений
**Как** владелец сервиса, **я хочу** задавать лимиты запросов и расходов, **чтобы** защищать бюджет и стабильность API.

Критерии: если владелец инстанса включает лимиты, они настраиваются по клиенту и времени; без явной конфигурации роутер не навязывает бюджетные лимиты на модели; секреты находятся вне репозитория. **P0**

## US-13. A/B-тесты и offline evaluation
**Как** владелец продукта, **я хочу** безопасно сравнивать новые модели и политики, **чтобы** улучшать маршрутизацию без скрытого ухудшения качества.

Критерии: shadow/offline-режим; сравнение качества, стоимости, latency и ошибок; критерии переключения и возможность отката. **P1**

## Предлагаемый MVP-срез
P0: US-01, US-02, US-03, US-05, US-06, US-08, US-09, US-11, US-12. P1: US-04, US-07, US-10, US-13. Для первого вертикального среза достаточно одного API-совместимого адаптера и mock endpoint. Архитектура должна позволять пользователю подключать произвольные модели и локальные endpoints; каталог, рекомендации, бюджетные ограничения и fallback не должны становиться обязательным белым списком или централизованным биллингом.
